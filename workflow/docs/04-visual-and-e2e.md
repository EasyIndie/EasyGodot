# 04 · 视觉层与 Headless E2E（阶段 3 沉淀）

> 视觉层是「薄渲染器 + 逻辑桥接」，所有规则判断仍走 core。
> 这让视觉层可被 Headless 直接实例化驱动，实现真正的 E2E 自动化。

---

## 1. 架构

```
scenes/
├── game.gd     # Game 节点：加载关卡 + 渲染棋盘/方块 + 移动桥接 + 胜负
├── main.gd     # 主场景：摄像机 + 光照 + Game + 键盘输入转发
└── main.tscn   # 根 Node3D（仅挂 main.gd，其余全部代码生成）
```

**职责边界**：

| 层 | 职责 | 依赖 |
|---|---|---|
| `core/` | 规则、状态、移动、判定 | 无（纯逻辑） |
| `scenes/game.gd` | 渲染 + 桥接（读 core 状态→摆网格；输入→core 移动） | core |
| `scenes/main.gd` | 场景装配 + 输入转发 | game |

## 2. 通用 PolyCube 渲染

不针对骨牌特判，而是**每个世界单元画一个 1×1×1 立方体**——对任意形状/方向
（骨牌竖立/横躺、Cube、未来的 Bar/L/T）都成立。

**坐标映射**：核心单元 `(x, y, z)` → 视觉位置 `(x, y+0.5, z)`（单元立方体中心在格子上方半格）。

```
核心 y=0（底层格）→ 视觉立方体 y∈[0,1]
核心 y=1（竖立上层）→ 视觉立方体 y∈[1,2]
棋盘瓦片 → 薄板 y∈[-0.2, 0]（顶面即方块底面）
```

配色：蓝灰棋盘格（明暗交替）/ 发光绿目标 / 黑洞 / 暖橙方块；通关时方块变绿。

### 翻滚与坠落动画

**规则与动画解耦**：`core/moves.gd::roll_delta()` 额外返回 `pivot`（前下边相对位置），
视觉层用它在「前下边」建一个枢轴节点，把方块挂上去绕枢轴转 90°：

```
pivot_world = Vector3(state.position) + roll_delta(...).pivot
绕 pivot 旋转 M 后的几何 == 新单元位置（已在数学上验证）
```

- **合法移动**：绕真正的底棱翻滚 90°（`ROLL_TIME=0.16s`）→ 吸附到新格。
  > 坐标注意：`roll_delta` 的 `pivot` 用「单元中心在整数格」坐标，而渲染把方块抬高 0.5 贴地，
  > 因此 `pivot_world` 要 **+0.5** 才是方块真正的底棱（否则会绕“底面下方 0.5”转，看着发扁）。
- **失去支撑（越界或黑洞）**→ 触发 `fell` → 失败。黑洞是“空洞”而非实心暗格，与越界同构，动画按支撑情况分两类：
  1. **完全悬空**（掉出棋盘 / 整块落在洞口）：原地**自由落体**（`y ∝ t²`）+ 绕翻滚轴自旋；
  2. **部分支撑**（一半悬在洞口/边界）：先绕**支撑边缘向空洞倾倒 90°**（支点不动，`TIP_TIME=0.3s`），
     脱离后再自由落体并继续翻转（`FALL_TIME=0.9s`）。

动画用「刚体节点」承载方块：翻滚阶段绕支点 P（`pos = P + R(θ)(C_s−P)`），
坠落阶段改为绕自身质心旋转 + 平移，因此不会出现“垂直穿过实心格”的穿模。

### 空洞（void）与「踩空坠落」

**空洞 = 地面缺失**，不是装饰性暗格；越界同样属于「没有地面」。因此：

- `board.is_solid()` / `supports()` 是「脚下有没有地面」的**唯一依据**，不需要任何“黑洞表”。
- **机关扩展点**：`board.set_void(cell2d, on)` 可把实心格动态变为空洞（或恢复），
  之后调用 `game.check_fall()` —— 若方块脚下已无地面就播放踩空坠落。
  为未来的机关（如可开关的地板）预留，无需改动画代码。
- 视觉上空洞就是**不铺地面**（该格直接留空、透出背景），一眼看出是“地面缺失”。

**关键设计**：core 的 `apply_move_on()` 对不合法移动仍返回 `null`（求解器不受影响），
「坠落」作为**游戏层规则**在 `game.gd::try_move()` 里用 `board.supports()` 判定——
保持规则核心纯净、可解性与视觉表现互不污染。

> `animate=false` 时所有移动同步执行，供 headless 测试做确定性驱动（不依赖帧推进）。

## 3. 输入映射与可玩 HUD

网格方向映射（与求解器 `DIR_LABELS` 一致）：

```
→ / D = +x      ← / A = -x      ↑ / W = -z      ↓ / S = +z
R = 重开        L / Esc = 选关界面（Esc 也用于关闭）
V = 回放本关最佳记录（无记录时无动作）
N / P = 下一关 / 上一关      1-9 = 跳到已解锁关卡      回放中 Esc = 退出回放
T = 切换触屏操作层（桌面调试用）
**触屏**：滑动屏幕 或 点按左下方向键；右下为「重开 / 选关 / 回放」
```

**Bloxorz 式斜 45° 等距视角**：摄像机位于棋盘 +X/+Z 角上方，棋盘呈菱形。
按键仍沿网格轴移动，因此在屏幕上表现为斜向（↑ 朝右上、→ 朝右下……），与经典 Bloxorz 一致。
该视角让方块与终点在屏幕上**天然错开**，竖立的方块不会挡住后方目标格（无需额外标记）。

> 视角参数见 `main.gd` 的 `_frame_camera()`（方位角 45°、俯角约 45°，按棋盘尺寸自适应）。
> 设计要点：容易与终点相邻的“1 步”关卡会天然遮挡，故关卡生成用 `--min-moves` 过滤掉退化布局。

**氛围与质感**（久看不累的关键）：
- **渐变背景幕布**：挂在相机前的 unshaded 全屏 quad（`main.gd::_setup_backdrop`）。
  > 踩坑：`gl_compatibility` 下 `Environment.BG_SKY` / ProceduralSkyMaterial **不会渲染**（已实测），
  > 所以改用一片跟随相机的渐变幕布，任何渲染后端都生效。
- **阴影**：方向光开 `shadow_enabled`；瓦片 `cast_shadow=OFF`（但接收），方块投影落在瓦片上 → 立体感。
- **目标格呼吸发光**：`game.gd::_process` 用正弦微调目标格自发光，吸引注意且不呆板。

**可玩 HUD**（CanvasLayer + 纯代码生成，圆角半透明面板）：
- 左上角：关卡编号 + **进度条**；右上角：步数 + **最佳 / 参考步数**（如 `最佳 12 · 已最优`）
- 通关时：方块**保持原位、不变色**；只做一次**灯光脉冲**（`main.gd::_win_beat`）确认落定，随后自动换关
- 坠落时：居中红字「坠落! 方块掉出了棋盘（按 R 重开）」
- **关卡过渡**：棋盘下沉 + 暗幕淡入（“关卡合拢”）→ 暗幕下换关并居中显示「关卡 N / M」→ 新棋盘降入 + 暗幕淡出（`main.gd::_transition_to`）
- 底部：操作提示（锚点定位、分辨率无关），**9 秒后自动变淡**以免长期干扰
- 关卡列表：自动扫描 `levels/*.json`（新增关卡无需改代码）

## 3b. 选关界面与回放（meta/）

**分层**：`meta/` 存放「元游戏层」，与规则层（`core/`）解耦，可 headless 单测。

| 文件 | 说明 |
|---|---|
| `meta/progress.gd` | 进度模型 + 持久化（`user://progress.json`）：已完成 / 最佳步数 / **最佳回放** / **本机榜（每关前 5 条）**；存档路径可注入 → 测试写临时文件 |
| `meta/level_select.gd` | 选关界面（CanvasLayer 覆盖层，纯代码构建） |
| `meta/leaderboard.gd` | 本地榜与总成绩汇总；含「将来 POST 给后端」的标准化载荷接缝 |

**选关界面**（`L` / `Esc`）：
- 卡片显示 **编号 / 形状（骨牌·方块）/ 状态**：已通关显示玩家最佳步数，未通关显示参考（最优）步数
- **顺序解锁**：第 N 关需第 N-1 关已通关；锁定的卡片 `disabled`（键盘导航自动跳过）
- 键盘（←↓↑→ + Enter）或鼠标点击；`重置进度` 需**连点两次**确认，3 秒后自动取消
- 打开时**隐藏游戏 HUD**，避免两层信息叠在一起
- **顶部汇总**：`已通关 N / M　·　总成绩 X 步　·　已最优 K 关`
- **底部详情条**：焦点/悬停在哪张卡片，就显示该关的形状 / 参考步数 / **本机榜**（如 `3 / 6 步`）

**回放**（`V`）：
- 通关时把本局移动序列（`moves.gd::direction_label` 的标签序列）记入进度；**仅当步数更短**才覆盖
- 回放 = 复位关卡 → 逐步 `try_move` 重演 → 顶部显示「回放 i / N」→ 结束提示 → 自动复位
- 回放期间**不记录进度、不触发自动换关**（`main.gd::_on_won` 内有 `_replaying` 分支）

**本地排行榜（对应 MVP 的「排行榜基础」）**：
- 每关保留**前 5 条**通关成绩（按步数升序），不只是最佳那一条
- **总成绩** = 各关最佳步数之和（类似速通的 Total Time，越小越好）；
  **已最优** = 最佳步数已达到参考（求解器最优）步数的关卡数
- **远端接缝**：`leaderboard.gd::submit_payload()` 给出将来 POST 的载荷形状
  （`{v, level, moves, at, player}`）。现在纯本地；接服务端时只需把该载荷发给后端并拉回榜单，
  界面无需改动（`level_select` 只依赖 `Leaderboard` 的取数接口）。

**关卡 key 约定** = 文件名去扩展名（如 `level_01`）：选关界面只扫描目录就能拿到 key，
不必加载完整关卡。关卡 JSON 里另存 `optimal_moves` / `difficulty` 作为**可再生的缓存元数据**
（由 `tools/build_level_set.gd` 写入，重建关卡集会随之刷新）。

## 3c. 触屏操作与移动端适配

**目标**：手机上打开网页版也能玩（没有键盘鼠标）。

**操作层** `meta/touch_controls.gd`（CanvasLayer，仅触屏设备显示）：

- **D-pad**：左下**斜向菱形**（↖↗↙↘）——摆在对角位置、用对角箭头，
  使得「按钮位置 / 箭头 / 方块去向」三者一致
- **动作按钮**：右下「重开 / 选关 / 回放」
- **滑动**：全屏滑动，`swipe_dir()` 把屏幕位移映射为网格方向

> **触屏必须按“屏幕方向”映射，不能沿用键盘的网格轴**：
> 斜 45° 等距相机下，四个网格方向在屏幕上成对角分布
> （`-z` 右上、`+x` 右下、`+z` 左下、`-x` 左上）。
> 如果照键盘那样「上滑 = -z」，方块会往**右上**滚，用户会觉得完全错位（真实反馈）。
> 现在屏幕方向由相机 `unproject` **现算**后注入操作层（`main.gd::_update_touch_screen_dirs`），
> 以后换相机/换取景也不用改映射。
> 完全竖直/水平的滑动会落在两方向的正中间（平局），按固定顺序取一个，保证同一手势结果稳定。
>
> **键盘仍按网格轴**（↑=-z…）：按下 `↑` 与点按 D-pad 的 `↗` 是同一个动作，两边效果一致。

**显示判定**：`DisplayServer.is_touchscreen_available()`；
可用 `?touch=1` / `?touch=0` 强制（便于在桌面调试触屏 UI），桌面按 `T` 切换。
选关界面打开时会一并隐藏控件，且触屏方向被拦下（不会穿透到棋盘）。

**布局自适应**（`meta/ui_layout.gd`，纯函数、可 headless 单测）：

| 函数 | 作用 |
|---|---|
| `camera_distance(board, aspect, fov)` | **按视口宽高比取景**：竖屏横向可视范围更窄，必须把相机往后拉，否则棋盘左右会被切掉；比例 ≥ 1 时由竖向决定（旧行为不变） |
| `touch_unit(viewport)` | 控件基准尺寸；横屏用更小系数，避免控件吃掉半个高度 |
| `level_grid(viewport, count)` | 选关网格列数与卡片尺寸随宽度降级（窄屏 3 列） |

**实测布局**（480×1040 竖屏 / 1080×500 横屏截图验证）：
棋盘完整可见并居中，控件贴左下/右下；触屏可点面积约 60 CSS px（远大于 44 px 的最低要求）。

### 状态提示的“提示带”（不要放屏幕正中）

早期把「坠落 / 通关」放在屏幕正中，会**直接压在棋盘上** —— 玩家看不到自己刚做了什么，
体验很差（真实反馈）。现在所有提示文字（操作提示 / 通关 / 坠落 / 回放进度）
统一由 `main.gd::_refresh_bands()` 放进一条**提示带**：

| 场景 | 提示带位置 |
|---|---|
| 桌面 | 底部（棋盘下方，原本操作提示的位置） |
| 触屏竖屏 | 顶部（HUD 下方；底部被 D-pad / 动作按钮占用） |
| 触屏横屏 | 底部（控件下方的一条窄带） |

同一时刻只显示优先级最高的一条（`坠落 > 通关 > 回放 > 操作提示`），不会互相压字；
`test_e2e` 里有一条断言专门守这件事：提示的垂直中心必须离屏幕中线 >25% 视口高。

## 4. Headless E2E 测试（test_e2e.gd）

测试组：

1. **Game 直驱**：实例化 Game（`animate=false`）→ 加载关卡 → 校验棋盘/方块节点数 →
   用求解器解路径逐条 `try_move()` → 断言获胜（验证视觉层与 core 协同）。
2. **坠落失败**：向越界方向 `try_move()` → 断言 `is_lost()`、坠落步不计入步数、
   失败后不再响应输入、重开可恢复。
3. **输入映射**：`event_to_dir()` 纯函数单测（键 → 方向）。
4. **主场景实例化**：`load(main.tscn).instantiate()` + `await process_frame`，
   断言 `_ready` 完成装配（game/棋盘/方块就位）。

**关键技巧**：E2E 的「输入序列」直接复用求解器的 `solution`——这使测试向量自动正确，
且与 Replay/Ghost/排行榜共用同一份数据。

**真实 headless 启动**（冒烟）：

```bash
godot --headless --no-header --path games/puzzle-core --quit-after 3 res://scenes/main.tscn
```

退出码 0、无报错。

**视觉截图**（对应五层测试的 Visual Test，AI 可据此做视觉回归）：

```bash
workflow/scripts/gf-shot.sh games/puzzle-core res://levels/level_04.json
# 输出 JSON + PNG，默认 <项目>/_shot.png
```

需要显示环境（WSLg/X11）；无头 CI 下不适用。

## 5. 阶段 3 沉淀的最佳实践

1. **视觉层保持薄**：渲染层不重复规则逻辑，只读 `core` 状态摆网格；换引擎渲染方式不影响规则。
2. **通用渲染胜过特判**：每单元立方体渲染天然支持任意 PolyCube，为未来形态扩展铺路。
3. **E2E 测试向量 = 求解器解**：不手写输入序列，避免测试与规则漂移。
4. **场景全部代码生成**：`.tscn` 只挂脚本，避免手工维护场景资源（利于 AI 生成与 diff）。
5. **`await process_frame`**：测试 `_ready` 装配的标准异步模式。
6. **动画与规则解耦**：core 只返回几何（`roll_delta` 含 `pivot`），动画在视觉层播放；
   `animate=false` 使测试同步、确定，不依赖帧推进。
