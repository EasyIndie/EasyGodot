# 10 · 关卡机制升级设计（多块棋盘 + 机关）

> 起因（用户 2026-10）：目前所有关卡都是「一块棋盘 + 空洞」，希望结合多块棋盘与各种机关提高趣味性，
> 并且**求解器要能自动适配**这些新关卡。
>
> 本文先给判断与取舍标准，再给落地设计。**取舍标准沿用本项目已经生效的那条硬规则**：
> 新东西必须制造一个**真实的推理约束**（姿态约束 / 占地约束 / 顺序约束），
> 否则就是装饰品，一律砍掉 —— cube 与冰面就是被这条规则砍掉的。

---

## 1. 结论先说

| 问题 | 回答 |
|---|---|
| 能不能做多块棋盘？ | **能，而且不需要改关卡格式**。「多块棋盘」= 网格内被空洞切开的**多块互不相连的区域**；靠「桥 / 传送门」在区域之间通行。真正的「多层高度」不建议现在做（见 §5）。 |
| 能不能加机关？ | **能**，但要挑。机制层（`mechanism_state`）当初刻意没预留字段，就是为了等到真正需要时**按需求设计**，而不是先摆一堆空壳。现在正是那个时候。 |
| 求解器能不能自动生效？ | **能，但有一个前提**：机关的开合/碎裂状态**必须进入 BFS 的状态键**。否则求解器会把「桥已开」和「桥已关」当成同一个状态，给出**错误的（不存在的）解**。这是本次改造最关键的一处，也是最容易做错的一处。 |

## 2. 三个机关（每个都过一遍「它制造什么推理」）

### ① 开关 + 桥（switch / bridge）— 打通多块棋盘的主力

- **规则**：方块占地覆盖开关格即触发；桥格在「开」时可站，在「关」时是空洞。
- **它制造的推理**：**顺序**。你不能先去 B 岛再去按开关（桥还不存在），
  也不能在桥还开着的时候去按第二次开关（会把自己脚下的桥关掉 → 坠落）。
- **状态必须进 BFS**：`开/关` 每一位都要进状态键。
- **为什么它值得做**：它是**唯一**能让互不相连的区域产生"通行权"的机制，是"多块棋盘"的钥匙。
- 变体：**闸门（gate）** 与桥相反 —— 按下开关后某处**变成**空洞（把路封死）。同一个机制的两种参数。

### ② 传送门（portal）— 姿态约束

- **规则**：一对（或多格循环）传送格；方块进入其中一格 → 出现在配对的另一格，姿态保持不变。
- **它制造的推理**：**姿态**。你的方块是「竖立（1×1 占地）」还是「平躺（1×2 占地）」直接决定
  你出现在对面之后**能不能继续动**（对面出口旁边只有 1 格宽 → 必须竖着进去）。
  这与整体玩法的主轴（姿态约束）是同一条，所以它是"长得像这个游戏的机关"。
- **状态必须进 BFS**：传送本身不改变状态，但**姿态**本来就在状态里 → 求解器天然正确。
- **不做**：随机传送、需要"充能"的传送门（没有可推理性，只有运气）。

### ③ 碎裂砖（fragile）— **已实现，然后整体删除**

规则很简单：方块**离开**该格时碎掉（变空洞）→ 路变成有向图。看起来很美，但用自动化判据一测就崩：

> 把碎裂砖换成**普通实心格**再解一次 → **最优解一模一样**。

原因很硬：**最优玩家本来就不会走回头路**，所以"会碎"这件事对最优解没有任何影响，
它只是惩罚乱走的玩家 —— 那是"手感"，不是"推理约束"。
按本项目的硬规则（**不制造必须推理的约束就砍掉**），它与 cube / 冰面同批处理：
规则、测试、渲染、文档**全部删除**，不留死代码。完整经过见 §7.4。

### 明确砍掉的（附理由，避免以后反复讨论）

| 机制 | 砍掉的理由 |
|---|---|
| 高度差 / 多层平台 / 电梯 | 会把「棋盘是平面」这个贯穿规则层与渲染层的前提打断（坠落判定、取景、稀疏化全要重写）。**收益（视觉新鲜）与代价不成比例**，不如先把机制与关卡做深。 |
| 冰面 / 传送带 / 重力块 | 都是「让方块自己动」，与"玩家一步一步决策"相冲突；冰面已经实测过 —— 更糟。 |
| 碎裂砖（fragile） | 见上：对**最优解**毫无影响（最优玩家不会回头），过不了"是否制造约束"这一关。已实现后删除。 |
| 移动平台 / 限时 / 倒计时 | 实时压力对解谜是干扰项；本项目也刻意没有时间压力设计（用时只作记录）。 |
| 随机传送、抽奖式机关 | 不可推理 = 不是谜题。 |
| 一次性钥匙/门 | 与「开关 + 桥」重复（都是"收集状态 → 改变通行权"），先做前者，避免两个机制做同一件事。 |

## 3. 「多块棋盘」怎么落地（不改关卡格式）

现在的关卡已经能表达多块区域：`grid` 是外框，`holes` 是挖掉的地。
**只要挖出一条贯穿的沟，剩下的就是两块互不相连的区域** —— 视觉上就是两块独立的平台。
所以"多块棋盘"要补的不是格式，而是：

1. **区域着色**：把彼此不相连的连通块分给不同色系（冷灰 / 暖灰 / 青灰），
   让"这是两块地方"一眼可见，而不是一片同色的棋盘上莫名有几个洞。
2. **连通手段**：桥（开关控制）/ 传送门 —— 有它们，区域之间的通行才成为谜题。
3. **区域标注**：关卡 JSON 里可以写 `regions: [{cells: [...], palette: 1}]`；
   **不写也能跑**（未标注 → 自动按连通块着色 + 默认配色）。

> 关卡格式保持向后兼容：老关卡（`grid` + `holes` + `goal`）**一个字节都不用改**，
> 新字段全是可选的。这是刻意的：20 关已经验证过的曲线与存档键都不能因为升级而失效。

## 4. 求解器与规则层怎么改（核心）

现状：`State = shape + orientation + position`，`canonical_key() = world_cells()`。
问题：加了机关之后，**同一组占用单元 + 不同的机关状态 = 两个不同的世界**。

改造（每一步都保持「纯函数 + 与引擎解耦」）：

```
MechState            # 机关状态：开关的开合（bits）+ 已碎格子（set）
  ├ key()            # 规范键（排序拼接）
  └ with_flag / with_broken / duplicate

Mechanisms           # 机关的数据表 + 纯规则
  ├ parse(list)                     # 从 JSON 解析并校验
  ├ is_solid(board, defs, mech, c)  # 含「桥的开合」与「已碎」
  ├ supports(...)                   # 占地是否全部有地面
  └ on_enter(...) -> MechState      # 踩上去之后发生什么（按开关 / 碎掉刚离开的格子）

Core.apply_step(board, state, mech, d) -> Dictionary | null
  ├ null                 : 这一步不可能（目标格在当前机关状态下没有地面）
  └ {state, mech, fall}  : fall=true 表示「落上去之后地面消失」（被自己的机关害死）
```

- **BFS 的状态键** = `state.canonical_key() + "|" + mech.key()`。
- 老 API `Core.apply_move_on(board, state, d)` 保留（内部用空 MechState），
  既有测试与生成器不用改 —— 但**游戏与求解器都走新 API**（单一实现）。
- `is_goal` 也要走机关层（闸门类机关可能让终点临时不可达）。

### 求解器要自动生效，还必须过这三关

1. **正确性**：机关状态进键（否则给出假解）。
2. **可解性判定**：BFS 到不了目标 → `solvable: false`（生成器会自动过滤掉这种关卡）。
3. **必要性判定（自动化"好不好玩"的过滤器）**：
   > 把关卡里的机关**全部关掉**再解一次：
   > - 关掉后**仍然可解且步数不变** → 这个机关是**装饰**，警告（生成器直接丢弃）。
   > - 关掉后**不可解**，或步数明显变长 → 机关是**承重的**，通过。
   
   这条把「好玩」里可以自动化的那部分变成了机器判据；剩下不可自动化的（观感、节奏）
   仍然交给人看图决定。

## 5. 渲染与手感（要跟规则一起改，否则机关看不见）

| 机关 | 画法 | 为什么 |
|---|---|---|
| 开关 | 琥珀色瓦片，被压住时更亮 + 轻微下沉 | 状态必须**一眼可见**，否则玩家不知道发生了什么 |
| 桥（关） | 半透明"幽灵框"（极薄的轮廓） | **必须让人知道这里将来会有路** —— 完全隐藏会让玩家以为那是个普通空洞 |
| 桥（开） | 青色实心瓦片（亮起时有一个短促的缩放动画） | 状态变化要有反馈 |
| 传送门 | 紫色 / 青色发光环，同色成对；进入时给一次闪光 | 配对关系必须能认出来 |
| 碎裂砖 | 灰白裂纹瓦片；碎掉时缩一下再消失 | "会碎"必须事先看出来，不能事后惩罚 |

规则：**机关的可视状态只能由状态推导，不能由"刚才发生了什么"推导**
（即：`mech` 变了就重画，而不是"播放一次动画就完事"）。
理由与庆祝动画那次踩的坑完全一样 —— 持久状态与一次性动画混在一起一定会出错。

## 6. 落地顺序（★=已完成）

1. **核心层**：`MechState` + `Mechanisms` + `Core.apply_step` + 求解器 + 关卡加载 + 质检
   （**纯逻辑、headless 可测、有 fixture 关卡**）。
2. **渲染层**：五种瓦片外观 + 状态变化动画 + `check_fall` 接上机关。
3. **一个手工机关关**：开关 + 桥（两块岛之间）+ 一个传送门 + 几块碎裂砖，
   跑 `validate_levels` 与求解器，确认"机关是承重的"。
4. **生成器**：在随机候选盘面上自动找**承重**机关位置（必要性判据做筛选），
   批量产出机关关候选；曲线仍按「棋盘面积 + 空洞密度 + 机关数」走。
5. ★ **混合进 20 关**（用户 2026-10 决定：不做独立章节）：
   第 1–12 关保持"纯空洞"（学习曲线），**第 13–20 关混入机关**（实际结果：13–17 传送门、18–20 开关+桥）。
   生成器会自动为这些关卡找**承重**的机关位置（见 §7.3）。

> 每一步都必须让 **12 套件 / 936 断言保持全绿**；新机制的每一条规则都要有断言，
> 并做**故障注入**验证（例如"故意不把机关状态放进状态键"必须让测试变红）。

### 7.0 "切沟 → 多块棋盘"（本轮新增的生成阶段）

机关的**位置**决定它是"摆设"还是"谜题"，而位置靠设计是设计不出来的。生成器现在这么做
（`tools/build_level_set.gd::_attach_trench_mechanism`）：

1. **切一条完整的沟**（整列变空洞，1~2 格厚），要求起点与终点分别在沟两侧 ——
   沟必须是**完整一列**，否则方块能绕过去（手推时踩过这个坑）。
2. 在沟上架**桥**（需要开关先打开）或放**一对传送门**。
3. **必需判据**：去掉机关后必须**不可解**（比"多走几步"更强的承重形式）。
4. 还要满足该关的步数目标，最后取最接近的一组。

结果：8 个机关关里 6 个是"必需机关"（15–20 关），另外 2 个是入门捷径。
**桥优先**：只要桥的位置通过了判据就直接采用 —— 因为桥是"顺序推理"的主力，
按分数比的话它永远会被传送门（位置多得多、步数还更短）挤掉（实测：不加这条，8 关全是传送门）。

### 7.0.1 本轮新增的三个真 bug（都藏在"看起来在工作"的表象里）

1. **生成器把 `holes` 写成字符串，加载器却照读不误**（最严重）
   切沟代码里的 `holes` 是 `Vector2i`，`JSON.stringify` 把它序列化成字符串 `"(7, 3)"`；
   加载器用 `h[0]/h[1]` 硬读 → `int("(") = 0` → **沟被静默读成完全不同的坐标**。
   关卡文件看着有洞、跑起来却不对，而且**一点报错都没有**。
   → 修：加载器只接受 `Vector2i` 或 `[x,z]`，其它一律报错（**坏关卡必须响亮失败**）；
   并加断言（`test_mechanisms::_test_bad_data_is_loud`，含 5 种非法形状）。
2. **残留的旧字段访问把整条搜索静默关掉了**
   `_pick_switch_cell` 里还留着按 `Vector2i` 取 `.x/.y` 的旧写法；格式改成 JSON 数组后它每轮都报错返回，
   于是**桥候选一次都没被验证过**。表面现象是"拒绝统计里完全没有 bridge" ——
   看着像"桥都被否了"，其实是根本没跑。
   → 教训：**工具的搜索必须带拒绝原因统计**（本轮靠它才定位到这两条）；
   以及"某类候选一条都没有"这种异常必须能一眼看出来。
3. **开关放错侧 / 放太远**
   开关必须放在**起点那一侧**（否则要先过沟才能按开关 = 死锁）、必须**在切沟之后依然可达**
   （用切沟后的空洞算可达性）、而且要**贴着沟**（离太远把关卡拉出目标区间）。
   三条都是"能跑但过不了判据"，靠拒绝原因统计才逐条暴露。

### 7.1 过程中抓到的两个真 bug（都由新断言/工具暴露）

1. **`is_solid` 的判定顺序错了 → 桥永远不可能存在**
   最初写成「先判静态空洞 → 再判机关」，于是**架在空洞上的桥**直接被判成没有地面：
   机关明明开着，方块就是过不去，而且**毫无报错**（静默错误最危险）。
   修正：补地类机关（bridge）必须早于静态空洞判定（桥的全部意义就是"在洞上补路"）。
   已加回归断言："洞上的桥打开后必须有地面"。
2. **机关效果按"占用单元"遍历 → 竖立方块把开关按了两次**
   竖立骨牌占两个单元但只占一格；按单元遍历时同一格开关被触发两次 = 翻转回原状
   （玩家会觉得开关坏了）。修正：机关一律按 **占地（去重后的 x,z）** 判定。
   这是对"唯一不变式 = world_cells()"的一次重要补充：**机关用占地，不用单元**。

### 7.2 自动化「好不好玩」的判据：机关是否**承重**

质检会把机关"对照关掉"再解一次（`solver/validate.gd::_control_board`）：

| 对照结果 | 判定 |
|---|---|
| 去掉机关后**不可解** | **承重**（最强）✓ |
| 去掉机关后**要更多步** | **承重（捷径）** ✓ ← 本次 13–20 关全部属于这一类 |
| 去掉机关后步数**完全相同** | **装饰品**（警告，生成器直接丢弃） |
| 去掉机关后**更短** | **添乱**（警告，必须回炉） |

> 这里也踩过一次：对照盘构造时写反了（把非 fragile 的机关留了下来），
> 于是"去掉机关后仍可解"永远成立，**所有机关都被误报成装饰品**。判据本身也需要测。

### 7.3 机关位置不是"设计"出来的，是**扫**出来的

手推几何极易写出"不可解"或"机关是装饰品"的关卡 —— 本轮我手推的三个候选**全部**被自动化工具否掉。
正确做法已经进了生成器（`tools/build_level_set.gd::_attach_mechanism`）：

1. 候选位置：桥只在**被 ≥3 个实心格包围的空洞**上试（填上它才可能真连出一条路）；
   开关/传送门放在实心格上。
2. 每个候选都跑质检：必须 `valid` 且**不能**出现 decorative / hurt 警告。
3. 还要满足该关的步数目标（机关会缩短最优解，所以基础盘面按「目标 + 3」生成）。
4. 取最接近目标的那组。

一次生成就得到 8 个带机关的承重关卡，全部通过曲线校验。**这就是机关关卡生成器。**

### 7.4 诚实的负面结论：碎裂砖被删除（不是"没时间做"）

`fragile`（离开即碎 → 单向路径）实现完、测试也写完，但用 §7.2 的判据一测：
**把碎裂砖换成普通实心格，最优解一模一样**。原因是结构性的 ——
最优玩家不会走回头路，所以"会碎"对最优解毫无约束，它只是惩罚乱走。
